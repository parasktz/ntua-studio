# NTUA STUDIO — Κρατήσεις βιντεοσκόπησης

Σελίδα κρατήσεων με ημερολόγιο και slots πραγματικού χρόνου, με σύνδεση αποκλειστικά μέσω ιδρυματικού email ΕΜΠ και έγκριση κάθε νέου χρήστη από τον διαχειριστή. Οι κρατήσεις αποθηκεύονται στο Firebase και η σελίδα φιλοξενείται δωρεάν στο GitHub Pages.

Αρχεία:

| Αρχείο | Ρόλος |
|---|---|
| `login.html` | **Αρχική σελίδα**: φόρμα ονοματεπώνυμου + email ΕΜΠ, αίτημα πρόσβασης, σύνδεση |
| `index.html` | Η σελίδα κρατήσεων (μόνο για συνδεδεμένους/εγκεκριμένους) |
| `calendar.html` | Μηνιαίο ημερολόγιο με τις δεσμευμένες ημέρες και ώρες |
| `admin.html` | Έγκριση αιτημάτων, λίστα κρατήσεων + CSV, κλείδωμα μη διαθέσιμων slots (μόνο διαχειριστές) |
| `auth.js` | Κοινή λογική σύνδεσης όλων των σελίδων |
| `config.json` | Όλες οι ρυθμίσεις — ημερομηνίες, ώρες, slots, Firebase |

## Πώς δουλεύει η σύνδεση

1. Ο χρήστης ανοίγει το `login.html` και συμπληρώνει **ονοματεπώνυμο** και **ιδρυματικό email** (…@ntua.gr ή σχολής, π.χ. @mail.ntua.gr — άλλες διευθύνσεις απορρίπτονται).
2. Το αίτημα εμφανίζεται στη σελίδα διαχείρισης. **Κανένα email δεν στέλνεται ακόμα.**
3. Ο διαχειριστής πατά «Έγκριση & αποστολή συνδέσμου» → ο χρήστης λαμβάνει email με σύνδεσμο σύνδεσης μίας χρήσης.
4. Πατώντας τον σύνδεσμο, ο χρήστης συνδέεται και μπαίνει στη σελίδα κρατήσεων. **Δεν υπάρχουν κωδικοί πρόσβασης πουθενά.**
5. Οι ήδη εγκεκριμένοι χρήστες παίρνουν νέο σύνδεσμο μόνοι τους από το `login.html`, χωρίς νέα έγκριση. Η «Απόρριψη» σβήνει το αίτημα (ο χρήστης μπορεί να ξαναϋποβάλει)· ανάκληση πρόσβασης γίνεται σβήνοντας την εγγραφή του από τον κόμβο `approved` στην κονσόλα του Firebase.

Τι αποθηκεύεται πού: στη **βάση των κρατήσεων** δεν μπαίνει τίποτα σχετικό με τη σύνδεση — ούτε κωδικοί (δεν υπάρχουν καν), ούτε sessions. Το επιβεβαιωμένο email τηρείται μόνο στην υπηρεσία **Firebase Authentication** ως ταυτότητα, και στους κόμβους `requests`/`approved` κρατιούνται ονοματεπώνυμο + email για τη διαδικασία έγκρισης. Σημείωση διαφάνειας: αυτό **δεν** είναι το επίσημο SSO του ΕΜΠ (login.ntua.gr) — κάτι τέτοιο θα απαιτούσε εγγραφή της εφαρμογής στο Κέντρο Δικτύων του ΕΜΠ. Η λύση επαληθεύει την κατοχή ιδρυματικού γραμματοκιβωτίου, που πρακτικά περιορίζει τη χρήση σε μέλη του ΕΜΠ.

## Βήμα 1 — Firebase (10 λεπτά)

1. Πήγαινε στο [console.firebase.google.com](https://console.firebase.google.com) και πάτα **Add project**. Δώσε ένα όνομα (π.χ. `ntua-studio`), το Google Analytics δεν χρειάζεται.
2. **Build → Realtime Database → Create Database**. Τοποθεσία `europe-west1`, ξεκίνα σε **locked mode**.
3. Στην καρτέλα **Rules** επικόλλησε τα παρακάτω και πάτα **Publish**:

```json
{
  "rules": {
    "bookings": {
      ".read": "auth != null && auth.token.email_verified === true && (auth.token.email.endsWith('@ntua.gr') || auth.token.email.endsWith('.ntua.gr')) && (root.child('approved').child(auth.token.email.replace('.', ',')).exists() || root.child('admins').child(auth.token.email.replace('.', ',')).exists())",
      "$date": {
        "$slot": {
          ".write": "auth != null && auth.token.email_verified === true && (auth.token.email.endsWith('@ntua.gr') || auth.token.email.endsWith('.ntua.gr')) && (root.child('approved').child(auth.token.email.replace('.', ',')).exists() || root.child('admins').child(auth.token.email.replace('.', ',')).exists()) && ((!data.exists() && newData.exists()) || (data.exists() && !newData.exists() && data.child('ts').val() - now > 172800000))",
          ".validate": "newData.hasChildren(['name', 'start', 'code', 'ts']) && newData.child('ts').val() > now"
        }
      }
    },
    "requests": {
      ".read": "auth != null && root.child('admins').child(auth.token.email.replace('.', ',')).exists()",
      "$key": {
        ".write": "(!data.exists() && newData.exists() && newData.hasChildren(['name', 'email']) && newData.child('email').val().toLowerCase().replace('.', ',') === $key && (newData.child('email').val().toLowerCase().endsWith('@ntua.gr') || newData.child('email').val().toLowerCase().endsWith('.ntua.gr'))) || (auth != null && root.child('admins').child(auth.token.email.replace('.', ',')).exists())"
      }
    },
    "approved": {
      "$key": {
        ".read": true,
        ".write": "auth != null && root.child('admins').child(auth.token.email.replace('.', ',')).exists()"
      }
    },
    "admins": {
      "$key": {
        ".read": true
      }
    }
  }
}
```

Με απλά λόγια: κρατήσεις διαβάζουν/γράφουν **μόνο** συνδεδεμένοι, εγκεκριμένοι χρήστες ΕΜΠ (με τους ίδιους περιορισμούς όπως πριν: δημιουργία μόνο σε ελεύθερο slot, ακύρωση μόνο όσο απομένουν πάνω από 2 μέρες — το `172800000` = μέρες × 86400000). Αίτημα πρόσβασης μπορεί να υποβάλει οποιοσδήποτε (μία φορά ανά email, με υποχρεωτικό όνομα και έγκυρη διεύθυνση ΕΜΠ), αλλά τα αιτήματα τα βλέπει και τα διαχειρίζεται μόνο διαχειριστής, και εγκρίσεις γράφει μόνο διαχειριστής. Στους κόμβους `admins`/`approved` δεν γράφει κανείς μέσω σελίδας εκτός των παραπάνω — τους διαχειρίζεσαι από την κονσόλα.

4. **Build → Authentication → Get started → Sign-in method**: πρόσθεσε τον πάροχο **Email/Password** και ενεργοποίησε ΚΑΙ τον διακόπτη **Email link (passwordless sign-in)** → Save.
5. **Authentication → Settings → Authorized domains**: πάτα **Add domain** και πρόσθεσε το domain της σελίδας σου, π.χ. `ΤΟ-USERNAME-ΣΟΥ.github.io`. Χωρίς αυτό, η αποστολή συνδέσμων αποτυγχάνει.
6. **Όρισε τον εαυτό σου διαχειριστή**: στο Realtime Database → Data, πρόσθεσε χειροκίνητα κόμβο `admins` και μέσα του ένα κλειδί με το email σου **με κόμματα αντί για τελείες** και τιμή `true`. Παράδειγμα για το `maria@central.ntua.gr`:

```
admins
  └─ maria@central,ntua,gr : true
```

(Τα κλειδιά της βάσης δεν επιτρέπουν τελείες — γι' αυτό οι σελίδες και οι κανόνες χρησιμοποιούν παντού αυτή τη μετατροπή.) Οι διαχειριστές έχουν αυτόματα και πρόσβαση χρήστη, χωρίς ξεχωριστή έγκριση.

7. **Project settings** (γρανάζι) → **Your apps** → εικονίδιο **`</>`** (Web) → Register app. Αντέγραψε τις τιμές του `firebaseConfig` στο τμήμα `"firebase"` του `config.json`. Πρόσεξε το `databaseURL` — αν δεν εμφανίζεται εκεί, θα το βρεις στη σελίδα του Realtime Database. (Τα στοιχεία αυτά είναι σχεδιασμένα για δημόσιες σελίδες — την προστασία την κάνουν οι κανόνες και η έγκριση.)

## Βήμα 2 — GitHub Pages

1. Φτιάξε νέο repository (π.χ. `studio-booking`) και ανέβασε τα 6 αρχεία (**Add file → Upload files**).
2. **Settings → Pages → Source: Deploy from a branch → Branch: main / (root) → Save**.
3. Σε 1–2 λεπτά η σελίδα θα είναι στο `https://ΤΟ-USERNAME-ΣΟΥ.github.io/studio-booking/login.html` — αυτό το link μοιράζεσαι. (Όποιος ανοίξει απευθείας το `index.html` χωρίς σύνδεση, μεταφέρεται αυτόματα στη σύνδεση.) Το ημερολόγιο είναι στο `.../calendar.html` και η διαχείριση στο `.../admin.html`.

Σημείωση: οι σελίδες δεν δουλεύουν αν τις ανοίξεις απευθείας ως αρχεία (file://) — δοκίμαζέ τες στο GitHub Pages ή με τοπικό server (`python -m http.server`).

## Βήμα 3 — Προσαρμογή στο config.json

| Ρύθμιση | Τι κάνει | Παράδειγμα |
|---|---|---|
| `dateRange` | Περίοδος κρατήσεων | `{"start": "2026-10-01", "end": "2026-12-10"}` |
| `openWeekdays` | Ανοιχτές ημέρες: 1=Δευτέρα … 7=Κυριακή | `[1, 2, 3, 4, 5]` |
| `excludedDates` | Αργίες / κλειστές ημέρες | `["2026-10-28", "2026-11-17"]` |
| `hours` | Ωράριο λειτουργίας | `{"start": "09:00", "end": "17:00"}` |
| `slotMinutes` | Διάρκεια κάθε slot σε λεπτά | `60` |
| `maxSlotsPerBooking` | Μέγιστα slots ανά υποβολή | `3` |
| `editDaysBefore` | Έως πόσες μέρες πριν επιτρέπεται ακύρωση/αλλαγή (άλλαξε και τον αριθμό στους κανόνες: μέρες × 86400000) | `2` |
| `dateOverrides` | Ειδικό ωράριο/διάρκεια/κλείσιμο για συγκεκριμένη ημέρα | δες παρακάτω |
| `fields` | Αν το email/τηλέφωνο εμφανίζεται ή είναι υποχρεωτικό στη φόρμα κράτησης | `{"email": {"show": true, "required": true}}` |

```json
"dateOverrides": {
  "2026-10-15": { "start": "10:00", "end": "14:00" },
  "2026-11-20": { "slotMinutes": 30 },
  "2026-12-04": { "closed": true }
}
```

## Κρατήσεις, αλλαγές, μη διαθεσιμότητα

**Κράτηση:** ο χρήστης διαλέγει ημερομηνία, έως 3 slots, και τα κλείνει με μία υποβολή. Κάθε slot γράφεται με transaction (μόνο αν είναι ακόμα ελεύθερο), οπότε δύο άτομα δεν κλείνουν ποτέ το ίδιο slot· η διαθεσιμότητα ενημερώνεται ζωντανά. Με την υποβολή δίνεται **κωδικός διαχείρισης** (π.χ. `K7F3-Q9ZM`).

**Αλλαγή/ακύρωση από τον χρήστη:** στο τμήμα «Έχεις ήδη κράτηση;» βάζει τον κωδικό, βλέπει τα slots του και ακυρώνει — έως `editDaysBefore` μέρες πριν την ημερομηνία τους, όριο που επιβάλλουν και οι κανόνες. Για αλλαγή ώρας: ακύρωση και νέα κράτηση. Χαμένος κωδικός βρίσκεται στην κονσόλα (πεδίο `code` του slot).

**Μη διαθεσιμότητα (διαχειριστής):** στο `admin.html`, πάνελ «Μη διαθεσιμότητα studio» — διαλέγεις ημερομηνία, πατάς slots (ή «Όλα τα ελεύθερα») και «Αποκλεισμός». Οι χρήστες τα βλέπουν ως **✕ Μη διαθέσιμο** και δεν τα κλείνουν. Άρση με κλικ στο κλειδωμένο slot· μέσα στο όριο των ημερών, μόνο από την κονσόλα. Ο διαχειριστής σβήνει οτιδήποτε, οποτεδήποτε, από την κονσόλα (Realtime Database → `bookings`).

**Ασφάλεια, με ειλικρίνεια:** πρόσβαση στα δεδομένα έχουν πλέον μόνο εγκεκριμένα μέλη ΕΜΠ, και η σελίδα διαχείρισης μόνο οι διαχειριστές — αυτά επιβάλλονται από τους κανόνες, όχι μόνο από τις σελίδες. Ο κωδικός διαχείρισης κράτησης προστατεύει από λάθη και απλή κακή χρήση μεταξύ εγκεκριμένων χρηστών· ένας κακόβουλος *εγκεκριμένος* χρήστης με τεχνικές γνώσεις θα μπορούσε να δει κωδικούς άλλων στη βάση. Για πανεπιστημιακό studio αυτό συνήθως αρκεί.
